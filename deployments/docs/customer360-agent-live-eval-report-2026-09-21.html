Caught & fixed The live eval found a production-breaking bug

On the first run with gpt-5.6-luna, every plan failed: UnsupportedParamsError — gpt-5.6-luna doesn't support temperature=0.4 while reasoning is active. The agent hard-coded temperature=0.4, which reasoning models reject. Fixed in ai_providers/base.py by enabling litellm.drop_params = True (drops any param a given model doesn't support instead of erroring). Both channels pass after the fix. Without this eval, the deployed agent would have 502'd on every request with the configured model.

Evaluation & findings

Both channels scored 7/7: well-formed JSON, on-spec keys, and closed-list guardrails respected (content IDs and the ZNS template came from the supplied candidates; all required ZNS params filled). Quality was notably strong — correct 2026 campaign dates and full Vietnamese localization matching locale: vi-VN.

Tradeoff Reasoning model: higher quality, ~4× the cost & ~2× the latency

vs the earlier gpt-4o-mini baseline, gpt-5.6-luna spends far more completion tokens (reasoning) and runs slower — but gets the year right (4o-mini dated campaigns in 2023) and localizes fully. Choose per use case: gpt-4o-mini for cheap/fast drafts, gpt-5.6-luna when correctness matters.

The agent only plans — it selects content and a schedule, it does not write email copy. Here's the whole path from that plan to a rendered email in one recipient's inbox, each step grounded in the real code.

Step 3 · the Approved template it links (crm_message_templates)

Copy is not AI-authored — the draft references an existing Approved template. Placeholders are {{ name }}-style.

subject:   We miss you, {{ first_name }} — 15% off your favourites
html_body: <p>Hi {{ name }},</p><p>Here's <strong>15% off</strong> your favourite skincare.</p>
           <p><a href="https://shop.example.com/winback">Shop now</a></p>
           <p><a href="{{ unsubscribe_url }}">Unsubscribe</a></p>
text_body: Hi {{ name }}, … Shop now: https://shop.example.com/winback
Step 4 · send-time render (backend-system/email_engine/rendering.py)

Design Plain {{ }} substitution — deliberately NOT Jinja

Rendering is a fixed regex substitution over a known context, not a template engine — so an AI/marketer-authored template can never execute code. Per-recipient context: {first_name, last_name, name, email, unsubscribe_url}. HTML-body values are HTML-escaped (a profile field can't inject markup); unknown placeholders render empty (no leaked {{ raw }}); then links are rewritten for click-tracking and a 1×1 open pixel is injected.

context (recipient "An Nguyễn"):
{'first_name': 'An', 'last_name': 'Nguyễn', 'name': 'An Nguyễn',
 'email': 'an.nguyen@example.com', 'unsubscribe_url': 'https://track…/u/unsub?u=TOK'}
Step 5 · final email in the inbox (actual output of the real render code)
From Skincare Co <hello@shop.example.com> To An Nguyễn <an.nguyen@example.com>
We miss you, An — 15% off your favourites

Hi An Nguyễn,

It's been a while. Here's 15% off your favourite skincare.

Shop now (href rewritten → track.example.com/c/click?u=…&url=…&k=<signed>)

Unsubscribe

+ 1×1 open-tracking pixel injected before </body> · links signed (k=) so the click endpoint rejects a swapped URL

subject and text_body render the same context unescaped; only the HTML body is escaped + tracking-wrapped. This is the exact output of email_engine.rendering run against the template + recipient above.

Zalo ZNS lifecycle — template-locked, no free text

ZNS is different from email: content is fixed by the OA-approved template. The agent picks one template_id and fills its typed params — it never authors message text, and there's no HTML, no link-rewrite, no open pixel. The Zalo OA renders its approved layout from the params.

1 agent /plan/zalo→ 2 crm_campaign draft · zalo_zns · InReview→ 3 human approve→ 4 bind params per recipient→ 5 send to Zalo OA
Step 2 · saved draft — crm_campaign linked to a zalo_zns template
{
  "crm_campaign": {
    "name": "Promo nudge", "status": "Draft", "approval_status": "InReview",
    "objective": "recover abandoned carts within 48 hours…",
    "template_id": "<approved zalo_zns template uuid>",
    "ai_plan": {

Step 3 · the Approved ZNS template (crm_message_templates · message_type ZALO_ZNS)

The template's layout/wording is locked by Zalo OA approval — only its declared params are fillable. metadata.zalo_template_id holds the OA template id the message is sent against.

variables (fillable params): ["offer", "expiry", "customer_name"]
metadata.zalo_template_id: <OA-approved template id>
status: Approved   message_type: ZALO_ZNS
(no subject / html_body / text_body — ZNS content is not authored here)
Step 4 · send-time param binding (notification_engine/rendering.py::render_params)

Design Only typed params are filled — no message body is ever authored

Each param value may carry {{merge}} tokens (first_name, last_name, name, phone) bound per recipient; non-string values pass through untouched. Recipients with no phone or zalo_opt_in=false are skipped. There is no HTML escaping / link rewriting / pixel — those are email-only.

context (recipient): {'first_name': 'An', 'name': 'An Nguyễn', 'phone': '+84901234567'}
template_data (before): {'customer_name': '{{ first_name }}', 'offer': 'Giảm 10%…', 'expiry': 'Trong 48 giờ…'}
